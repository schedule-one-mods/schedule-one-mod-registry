# Schedule I Mod Registry

The community-maintained directory consumed by [Schedule I Mod Manager](https://github.com/schedule-one-mods/schedule-one-manager). This repository registers mod identities and release discovery rules. Source and packages stay in each author's public repository.

Schema **2** has one entry per mod: stable `id`, `package_name`, display metadata, repository, and `release_source`. All current entries use GitHub Releases. `release_source.latest: github_latest` delegates the latest marker to the author's GitHub Latest release, avoiding a stale hardcoded version in the index. The index does not enumerate release numbers. It rejects the old schema rather than maintaining a second format.

When Browse is refreshed, the manager reads the index, lists published GitHub Releases, and reads `packaging/compatibility.json` from each `v<major.minor.patch>` tag. It derives the ZIP name from `{package_name}-{version}-{backend}.zip`. GitHub's asset size and SHA-256 digest bind each download to the discovered release; the imported manifest and compatibility must match. No repository-wide scans, GitHub Actions, server jobs, accounts or tokens are needed. Bare tags and arbitrary Git commits do not contain downloadable compiled packages and are not listed.

Each version shows its declared tested Schedule I versions, backend and MelonLoader versions. Claims come from the publisher; directory review does not independently verify every future release. Missing metadata, invalid digests or mismatched packages cannot become verified downloads. A failed release is reported without hiding other valid releases or other mods. If Latest is invalid, the manager does not label an older version Latest. Prereleases are selectable and marked, and are not selected automatically. Currently version tags have three numeric components; GitHub's prerelease flag is supported, suffixed version tags are not.

My mods groups downloads by package identity. Several versions can be stored, one can be enabled. Each version can be disabled or deleted; deleting the whole mod removes all local versions, while Browse continues listing it. Active managed copies are disabled before deletion. Changed managed files block deletion. Future mod packs can pin a stable mod ID, version and asset digest without changing directory entries; sharing and loading packs are not implemented here.

The manager reads `index.json` on main through the GitHub Contents API, with the raw URL for that same file as a transport fallback. Releases are queried only for registered repositories, on refresh. Release history is paginated up to 1,000 entries per mod with an explicit notice if truncated. GitHub rate limits or network failures are displayed; downloaded packages remain available offline.

See [CONTRIBUTING.md](CONTRIBUTING.md), [schema v2](schema/registry-v2.schema.json), and run `python validate.py` for offline validation. Register once by PR; publish subsequent releases in your own repository without a registry PR. Registry changes are needed for identity, display metadata, repository or discovery policy changes. Coordinate the v2 registry publication with the v2-capable manager release.
