# Register once, publish independently

1. Use a public GitHub repository with source and a stable package name. Prepare a manager-format ZIP containing `manifest.json`, `compatibility.json`, and exactly one `Mods/*.dll`. Optional README, changelog, icon and third-party notices are supported. Do not include game files, saves, SDKs or the loader.
2. Commit the release's compatibility JSON at `packaging/compatibility.json` (or another registered safe relative JSON path). Tag that exact source `v<major.minor.patch>`, for example `v0.1.4`. The tested game/backend/platform/loader values must match the JSON inside the ZIP. Claim only tested versions; unknown versions remain unverified.
3. Publish a GitHub Release for the tag and upload `{package_name}-{version}-{backend}.zip`, for example `Businesses-0.1.4-IL2CPP.zip`. The package manifest name/version must match. GitHub exposes the uploaded ZIP's SHA-256 digest and byte size. Releases missing a digest cannot be downloaded by the manager. Source-code ZIPs are not mod packages. Never move published tags or replace assets: publish a new version. Enable GitHub immutable releases if appropriate for your project.
4. Mark your intended stable release Latest in GitHub. Older releases remain downloadable. Use GitHub's prerelease flag for experimental releases; tags still need three numeric version components. Latest and compatible are separate concepts: the latest release is not assumed to work with every game version.
5. Fork this directory and add ONE entry in `index.json` following the current examples. Pick a stable lowercase hyphenated ID and unique package name. Set `release_source.type` to `github_releases`, `latest` to `github_latest`, your tagged `compatibility_path`, and the supported asset template. Run `python -m pip install -r requirements.txt` and `python validate.py`. Open the initial registration PR with source/license and test evidence.

For every later release, repeat steps 2–4 in your own repository. No registry PR, scanning service or GitHub Actions workflow is required. The manager discovers updates on Browse refresh. The registry's latest field describes an authoritative resolution policy rather than copying a version number that would need another PR. Compatibility is release-specific rather than inherited from the newest release or the main branch.

Reviewers approve the repository registration and its discovery contract. Future releases are publisher supplied, not separately registry reviewed. Byte integrity checks do not establish that executable code is safe. If a repository or discovery policy changes, submit a registry PR.

Supported today: Windows x64, IL2CPP or Mono metadata, one mod DLL per package, MelonLoader-only dependencies. The initial registered mods target IL2CPP. Mod packs and additional package hosts are future work.
